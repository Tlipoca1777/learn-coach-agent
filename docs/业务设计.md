# 学习教练 · 业务设计

> **定位**：一个记得你学习进度的 AI 教练 —— 它知道你哪里薄弱、什么时候该复习、
> 用什么方式讲你才听得懂。
>
> **相关文档**：[`记忆架构设计.md`](记忆架构设计.md) —— 四层记忆的设计基础
> **实现时间**：第 2 周 D9、第 3 周 D15–D17

## 1. 为什么这个业务必须靠长期记忆

这是整个业务设计里**最重要的一节**。因为如果答案不成立，记忆层就是装饰品。

| 能力 | 无记忆版（普通 ChatGPT） | 有记忆版（本项目） |
|---|---|---|
| 出题 | 你每次都要说"给我出几道 Python 的题"，然后它随机出 | 主动说"你上次在『生成器 yield』上卡住了，今天练两道？" |
| 讲解 | 通用讲法，可能用你不熟的语言举例 | 知道你是 Java 出身，用 `Stream` 类比生成器 |
| 复习 | 你自己记着要复习什么 | `/due` 直接列出今天该复习的，按遗忘曲线排好 |
| 诊断 | 你答错了，它说"再想想" | "这是你第三次在闭包的作用域上出错了，我们从头捋一遍" |
| 进度 | 没有任何积累 | 每个知识点的掌握度曲线，一眼看出进步 |

**因果链**：
```
没有长期记忆 → 每一次对话都是"第一次见面" → 只能提供通用问答
有长期记忆   → 它知道你的历史 → 能做出"个性化决策"（出哪道题、怎么讲）
```

这就是为什么这个业务选得对：**它的核心价值完全建立在"记得住"之上。**

## 2. 核心功能

### F1. 自适应出题（按薄弱点优先）

选题优先级 = 到期复习 > 薄弱知识点 > 没练过 > 已掌握但久未练。

**打分公式**（简单、可解释）：
```python
priority = (1 - mastery) * 0.6 + min(overdue_days / 7, 1.0) * 0.4
```
- `mastery`：掌握度 0~1，越低越该练
- `overdue_days`：距下次复习逾期多少天，除以 7 天封顶

选 `priority` 最高的知识点出题。**出题时告诉用户为什么选它**——这是让"记忆"可见的关键。

### F2. 掌握度追踪

每个知识点维护一个 0~1 的掌握度，随答题结果更新：

```python
答对（score=1.0）：mastery += (1 - mastery) * 0.3
半对（score=0.5）：mastery += (1 - mastery) * 0.15
答错（score=0.0）：mastery *= 0.5
```

为什么用这个公式：
- **答对时**：越接近 1 涨得越慢（`(1-mastery)` 是递减的）—— 防止"蒙对一次就变专家"
- **答错时**：直接砍半，衰减快 —— 错误是更强的信号

分档：
| 掌握度 | 状态 | 行为 |
|---|---|---|
| ≥ 0.8 | 已掌握 | 复习间隔拉长，只在到期时出现 |
| 0.4 ~ 0.8 | 学习中 | 正常复习节奏 |
| < 0.4 | **薄弱** | 优先出题，讲解时更详细 |

### F3. 间隔重复（SM-2 简化版）

每个知识点记住三个数：`interval_days`（当前间隔）、`ease`（难度系数）、`due_at`（下次复习时间）。

```python
答对：
    correct_streak += 1
    if streak == 1:   interval = 1      # 明天
    elif streak == 2: interval = 3      # 三天后
    else:             interval = interval * ease
    ease = min(3.0, ease + 0.1)         # 这道题对你变简单了
答错：
    correct_streak = 0
    interval = 1                        # 明天重来
    ease = max(1.3, ease - 0.2)         # 变难了
due_at = now + interval 天
```

> **不要上贝叶斯或 FSRS**。SM-2 的简化版已经足够体现"间隔重复"的思想，
> 而且面试时你能把公式讲清楚——比用了一个自己都说不清的库强得多。

### F4. 苏格拉底式追问

**答错时不直接给答案**，而是按这个顺序：
1. 指出具体错在哪（不是"错了"，而是"你把 `yield` 当成了 `return`"）
2. 给一个更小的提示（"想想一个函数里有多个 `yield` 时会发生什么"）
3. 如果第二次还错，才给完整解释

这条规则写在系统提示词里，并由 `record_answer` 的 `verdict` 字段驱动。

### F5. 用你熟悉的语言类比

用户画像里记着"Java 背景"，讲解时优先用 Java 类比：

| Python 概念 | Java 类比 |
|---|---|
| 生成器 / `yield` | `Stream` 的惰性求值（但 `yield` 能暂停/恢复） |
| `Protocol` | `interface`（但结构化，不用显式 `implements`） |
| `@property` | getter/setter（但是语法级的） |
| `with` | try-with-resources |
| 装饰器 | 注解（但运行时可执行） |
| 列表推导式 | `Stream.map().collect()` |

这张表存在画像/知识库里，模型讲解时可以参考。

## 3. 数据模型（新增 4 张表）

复用已有的 `sessions` / `messages` / `summaries` / `facts` / `profiles`，新增：

```sql
-- 知识点（树状，用 category 归类）
CREATE TABLE topics (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    name          TEXT NOT NULL UNIQUE,     -- "python.generator"
    display_name  TEXT NOT NULL,            -- "生成器与 yield"
    category      TEXT NOT NULL,            -- "python" / "llm" / "memory" / "fastapi"
    description   TEXT,
    created_at    TEXT NOT NULL
);

-- 题库
CREATE TABLE quiz_items (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    topic_id        INTEGER NOT NULL REFERENCES topics(id) ON DELETE CASCADE,
    question        TEXT NOT NULL,
    expected_answer TEXT,
    difficulty      INTEGER NOT NULL DEFAULT 1,   -- 1~3
    source          TEXT,                          -- 'seed' / 'generated'
    created_at      TEXT NOT NULL
);

-- 答题记录（这是"长期记忆"在业务侧的载体）
CREATE TABLE attempts (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    topic_id     INTEGER NOT NULL REFERENCES topics(id) ON DELETE CASCADE,
    quiz_item_id INTEGER REFERENCES quiz_items(id) ON DELETE SET NULL,
    question     TEXT NOT NULL,
    user_answer  TEXT,
    verdict      TEXT NOT NULL,               -- 'correct' / 'partial' / 'wrong'
    score        REAL NOT NULL,               -- 0.0 ~ 1.0
    feedback     TEXT,
    created_at   TEXT NOT NULL
);

-- 掌握度（每个知识点一行，答题后更新）
CREATE TABLE topic_mastery (
    topic_id       INTEGER PRIMARY KEY REFERENCES topics(id) ON DELETE CASCADE,
    user_id        TEXT NOT NULL DEFAULT 'default',
    mastery        REAL NOT NULL DEFAULT 0.3,
    attempt_count  INTEGER NOT NULL DEFAULT 0,
    correct_streak INTEGER NOT NULL DEFAULT 0,
    interval_days  REAL NOT NULL DEFAULT 1.0,
    ease           REAL NOT NULL DEFAULT 2.5,
    due_at         TEXT,
    updated_at     TEXT NOT NULL
);
```

**schema 版本要 +1**，并在 `_check_schema_version()` 里给出清晰的迁移提示。
（这是你第一次改 schema —— 正好练一下"数据库升级"这件事。）

初始化数据：约 **30 个知识点 + 60 道题**，覆盖：

| 分类 | 知识点示例 |
|---|---|
| `python` | 列表推导式、生成器与 yield、装饰器、`with` 语句、可变默认参数陷阱、闭包与作用域 |
| `llm` | token 与上下文窗口、temperature、结构化输出、prompt 工程、幻觉与缓解 |
| `memory` | 滑动窗口、递归摘要、向量检索、余弦相似度、时间衰减、去重与冲突消解 |
| `fastapi` | 路由、依赖注入、pydantic 模型、SSE 流式 |
| `project` | **这个项目本身的设计问题**（最好的复习材料） |

> 最后一行是关键：**用它复习你自己的项目**。面试前刷一遍 `project` 分类，
> 相当于自动生成面试题库。

## 4. 工具清单（Function calling 注册项）

> **总数锁定为 5 个**（原设计 9 个）。砍工具是为了给"规则版冲突消解 + 多用户隔离"腾时间，
> 详见 项目计划文档第 3.4 节。
> 工具少了不会削弱业务 —— 关键是**每个工具都提供模型决策所必需的事实**。

### 业务工具（3 个）

| 工具 | 签名 | 说明 |
|---|---|---|
| `record_answer` | `(topic_name, question, user_answer, verdict, score, feedback)` | 记录答题，更新掌握度和间隔重复。**必须每次判定后都调用**，否则业务失效 |
| `get_weak_topics` | `(limit=5)` | 按掌握度升序返回薄弱知识点 |
| `get_due_reviews` | `(limit=10)` | 返回 `due_at <= now` 的知识点，按逾期天数降序 |

> `get_progress_overview` 被砍掉了。它只是把已有数据汇总一下，而模型可以直接用
> `get_weak_topics` 的结果回答"我学得怎么样"。**能用一个工具做到的事不要开两个。**

### 通用工具（2 个）

| 工具 | 说明 |
|---|---|
| `calculator` | 让模型会算数（也用来做"回答正确率"这类小计算） |
| `get_current_time` | 简单，用来先跑通工具循环；间隔重复也需要"今天"这个概念 |

> `recall_memory` 被砍掉了（原设计里"把记忆检索做成工具"）——因为**记忆是无条件注入 prompt 的**
> （见第 8 节），既然已经有记忆在上下文里，再开一个回忆工具是重复的。
> 这个取舍值得记下来：*"工具化"不是越多越好，要看数据是否已经在上下文里了。*
>
> `search_quiz_bank` 也砍了：题库题目由 `get_weak_topics` 返回的知识点直接带出，
> 不需要模型再发起一次取题。

### 关于"谁来决定练哪个"的设计选择

有两种做法，**建议选第二种**：

- **做法 A**：做一个工具 `next_question()`，内部完成全部选题逻辑
- **做法 B**：给模型 `get_weak_topics` / `get_due_reviews` 两个**事实查询**，
  让**模型自己决定**练哪个，并说明理由

**选 B 的理由**：把决策权留给模型，你的代码只提供"事实"。
这样更容易调试（能看到模型为什么选这个），也更符合 Agent 的设计哲学。
做法 A 是"把智能写在代码里"，做法 B 是"把智能留在模型里"——面试时可以聊这个取舍。

⚠️ 选 B 的代价：**必须把选题规则写进系统提示词**（见第 5 节），
否则模型可能一直挑最简单的题，你就看不到"自适应"的效果了。

## 5. 系统提示词设计要点

```
你是用户的学习教练。你的职责是帮他掌握知识，而不是给他答案。

【教学规则】
1. 用户答错时，先指出具体错在哪，给一个更小的提示，让他再试一次。
   只有在第二次仍然答错时才给出完整解释。
2. 讲解新概念时，先调用 get_user_background 看他熟悉什么语言/工具，
   优先用他熟悉的东西做类比。
3. 每次讲解或出题前，先调用 recall_memory 看他之前在这个话题上
   说过什么、错过什么。

【记忆规则】
4. 出题时优先练他薄弱的和到期的。调用 get_weak_topics / get_due_reviews
   拿到事实，然后自己决定练哪个，并**说明为什么选它**。
5. 每次判定完用户答案，必须调用 record_answer 记录下来 ——
   不记录就等于没发生过。
6. 如果记忆里有信息，显式用上它（"你上次提到……"）。
   不要假装记得，也不要明明有记忆却不用。
```

**三条最容易出问题的规则**（都要写进提示词）：
1. **必须调 `record_answer`** —— 否则答题记录丢了，整个业务失效
2. **不要直接给答案** —— 模型天然倾向于"直接答"，必须明确禁止
3. **要用上记忆** —— 明明检索到了记忆却不用，等于白做

## 7. 评测方法（第 3 周 D18）

**对比实验：无记忆 vs 有记忆**

写法：准备 20 条模拟答题历史，然后各跑 20 次"出一题"：

| 配置 | 出题的来源 |
|---|---|
| 无记忆版 | 完全随机选题 |
| 有记忆版 | 按 `priority` 打分选题 |

**指标**（这两个指标最能说明问题）：

| 指标 | 含义 | 期望 |
|---|---|---|
| **薄弱覆盖率** | 出的题里，落在"掌握度 < 0.4"知识点的比例 | 有记忆版显著更高 |
| **无效出题率** | 出的题里，落在"掌握度 ≥ 0.8"知识点的比例 | 有记忆版显著更低 |

> 这两个指标的好处：**不需要 LLM 参与评测**，纯逻辑对比，完全可复现。
> 比"让模型打分"这种含糊的评测方式可信得多。

另外做一组记忆层的对比（沿用已有工具）：**有记忆 vs 无记忆的跨会话问答准确率**。

## 8. 与记忆层的接口（不用改记忆层）

这张表说明**为什么业务层是"插件"而不是"改造"**：

| 业务需要 | 用记忆层的什么 | 需要改记忆层吗 |
|---|---|---|
| 记住用户是 Java 出身 | `UserProfile`（第 3 周 D15）+ `LongTermMemory` | 否 |
| 记住"他上次在生成器上卡住" | `LongTermMemory.add("在……上卡住", "生成器 yield")` | 否 |
| 跨会话知道他的学习进度 | `topic_mastery` 表（业务自己的表） | 否 |
| 讲解前回忆相关历史 | `LongTermMemory.search()` 或 `recall_memory` 工具 | 否 |
| 追踪他的学习目标 | `UserProfile.goals` | 否 |
| 判断该复习什么 | `topic_mastery.due_at`（业务自己的逻辑） | 否 |

**一行记忆层的代码都不用改。** 这就是第 6 轮做依赖注入和分层设计的回报。

## 10. 这个业务在面试里的讲法

> "我做的不是通用聊天助手，是一个**学习教练**。
>
> 选这个方向是因为它的核心价值完全建立在长期记忆之上 —— 如果记不住你的历史，
> 它就只能提供通用问答；记住之后，它能做出个性化决策：今天该练哪个知识点、
> 用什么类比讲你才懂、你第三次在同一个概念上出错时要换个讲法。
>
> 我实现了掌握度追踪和 SM-2 简化的间隔重复调度，并且做了一个对照实验：
> 有记忆版出的题里，落在薄弱知识点的比例是 X%，无记忆版只有 Y%；
> 而在已经掌握的知识点上出题的比例，有记忆版低了 Z% —— 这说明记忆确实
> 在驱动有效的决策，而不是装饰品。
>
> 架构上一个关键点是：**业务层是通过工具注册插进来的，一行记忆层的代码都没改。**
> 这说明前面做的分层和依赖注入是有效的。"
