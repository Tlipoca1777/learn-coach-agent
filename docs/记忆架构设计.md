## 1. 问题定义

大模型是无状态的。要让对话有连续性，必须把历史重新塞进 prompt。这带来一个三角矛盾：

```
        记忆完整度
         （记得越多越好）
             ▲
            ╱ ╲
           ╱   ╲
          ╱     ╲
         ╱  矛盾  ╲
        ╱         ╲
       ▼───────────▼
   成本/延迟      上下文窗口
   （越少越便宜）   （有硬上限）
```

三个朴素方案都不能解决问题：

| 方案 | 致命缺陷 |
|---|---|
| 全量历史塞回去 | token 线性增长，聊 100 轮就爆窗口，成本不可控 |
| 只保留最近 N 条 | 中英文单条长度差异巨大，预算失控；且彻底丢掉长期信息 |
| 只保留最近 N 个 token | 丢掉的旧信息永久消失，"上次说的那件事"永远想不起来 |

**本项目的答案**：把"记忆"拆成四层，每层用最适合它的技术处理，再用一个统一的预算表把它们拼进一次请求。

## 2. 总体架构

```
                             用户输入
                                │
                                ▼
                   ┌────────────────────────┐
                   │   Memory Router        │  ← 决定这轮注入哪些记忆
                   │   记忆路由与预算分配     │
                   └───────────┬────────────┘
                               │
        ┌──────────────┬───────┴───────┬──────────────┐
        ▼              ▼               ▼              ▼
 ┌────────────┐ ┌────────────┐ ┌────────────┐ ┌────────────┐
 │ 短期记忆    │ │ 中期摘要    │ │ 长期记忆    │ │ 用户画像    │
 │ 滑动窗口    │ │ 递归压缩    │ │ 向量检索    │ │ 结构化JSON  │
 │            │ │            │ │            │ │            │
 │ 内存+SQLite│ │ SQLite     │ │ Chroma     │ │ SQLite     │
 └────────────┘ └────────────┘ └────────────┘ └────────────┘
        │              │               │              │
        └──────────────┴───────┬───────┴──────────────┘
                               ▼
                   ┌────────────────────────┐
                   │   Prompt 组装器         │  ← 按 token 预算裁剪
                   └───────────┬────────────┘
                               ▼
                   ┌────────────────────────┐
                   │   LLM（含工具调用循环）  │
                   └───────────┬────────────┘
                               ▼
                   ┌────────────────────────┐
                   │   记忆写入管线          │  ← 抽取·去重·冲突消解
                   └────────────────────────┘
```

**两条关键路径**：
- **读路径（每轮都走）**：路由 → 各层取回 → 预算裁剪 → 组装 prompt
- **写路径（每轮或异步）**：抽取事实 → 去重 → 冲突消解 → 落库 → 更新画像

## 3. 各层详细设计

### 3.1 短期记忆（ShortTermMemory）

**职责**：保证对话连贯性。存最近几轮的原文。

| 项 | 设计 |
|---|---|
| 存储 | 内存列表（当前会话）+ SQLite（持久化） |
| 容量 | `max_tokens` 预算内，另加可选的条数上限 |
| 淘汰 | 从最老的开始，装不下就停（不跳过） |
| 特殊 | system prompt 独立存放，永不被裁 |

**关键决策**：

- **按 token 预算而不是条数裁剪**。理由：一条 5 字消息和一条 5000 字消息都算"1 条"，
  按条数会让预算完全失控。实测数据见第 9 节。
- **装不下就停，不跳过**。对话是连续的，跳过中间一条会让上下文断裂，模型会困惑。
- **最新一条超预算也要保留**。否则用户刚问的问题被丢掉，功能直接坏掉。
  代价是 token 可能超预算，所以上层必须留安全余量。
- **接口允许注入 `token_counter`**。这让测试可以用确定性假计数器，
  不受估算算法变化影响。这是"依赖注入"在测试上的典型应用。

**接口**：
```python
class ShortTermMemory:
    def __init__(self, max_tokens: int, system_prompt: str | None = None,
                 max_messages: int | None = None,
                 token_counter: Callable[[list[dict]], int] | None = None): ...
    def add(self, role: str, content: str) -> None: ...
    def get_window(self) -> list[dict]: ...   # 返回副本
    def clear(self) -> None: ...              # 保留 system
    @property
    def token_count(self) -> int: ...
```

**淘汰消息的去向**：不丢弃，交给中期记忆做摘要。

> **实现细节（与最初设计的差异）**：原设计打算用 `on_evict` 回调，
> 实际改成了**按「已压缩到的消息 id」（`covered_until`）桥接**。
> 原因：回调是内存态，程序重启后就断了；而记忆必须能跨会话恢复，
> 所以桥接点要落在**数据库里能持久化的位置 id** 上，不能是内存回调。

### 3.2 中期摘要（SummaryMemory）

**职责**：把被挤出的历史压缩成一段摘要，保住要点，丢掉寒暄。

| 项 | 设计 |
|---|---|
| 存储 | SQLite `summaries` 表 |
| 生成 | LLM 递归增量压缩 |
| 触发 | 被挤出消息累积超过阈值；引擎按 prompt 总预算动态推导 |
| 容量 | 摘要本身受 token 上限约束；当前实现超长时截断并加省略号，二次 LLM 压缩仍是扩展方向 |

**为什么是"递归增量"而不是"一次性重压"**：

- 一次性把全部历史丢给模型压缩：历史越长越贵，且模型会丢细节，早期信息被反复稀释
- 递归增量：`新摘要 = LLM(旧摘要 + 新增的待压缩消息)`
  - 成本恒定（每次只处理一小段）
  - 旧摘要被反复"强化"，重要信息不容易丢

**代价**：递归摘要会累积误差（摘要的摘要）。当前缓解手段是 prompt 明确要求保留事实性信息（人名、偏好、决定、时间），丢弃寒暄和重复；评测集计划验证早期信息能否在长对话后召回。结构化输出（分「事实」「决定」「待办」三段）仍是后续改进方向，当前实现尚未采用。

**当前实现（2026-10-09）**：`SummaryMemory` 已实现，并通过 `tests/test_summary.py` 的 42 项测试。模块维护待压缩消息队列；默认摘要上限为 800 token、触发阈值为 400 token，引擎会按总 prompt 预算推导实际配置。system 消息和空白内容不会入队；达到阈值后才压缩。摘要失败或返回空白时保留旧摘要和队列以便重试，超长响应会截断并加省略号。`restore()` 用于从 SQLite 中恢复摘要和消息覆盖位置。

当前 prompt 使用保留/丢弃清单，但输出是自由文本，并未强制「事实 / 决定 / 待办」的结构化字段。D2 单元已完成；D3 长期记忆基础层、D4 评分/治理层和 D5 事实抽取均已完成。D6 已使用真实 SQLite、Chroma 和四个记忆模块验证事实抽取、检索注入、摘要生成及重启恢复；离线 CLI 的中文对话、`/status` 与 `/memory` 也有集成测试覆盖。详细测试入口见 `tests/test_integration.py`。

**摘要 Prompt 设计要点**：
```
你是对话摘要器。把下面的对话压缩成简洁摘要；摘要最终上限为 {n} token。

必须保留：
  - 涉及的人物、地点、时间
  - 用户的偏好、厌恶、习惯
  - 已经做出的决定和承诺
  - 未完成的待办

可以丢弃：
  - 寒暄、客套
  - 重复表述
  - 与用户长期信息无关的临时内容

已有摘要（在此基础上增量更新）：
{old_summary}

需要合并的新对话：
{new_messages}
```

### 3.3 长期记忆（LongTermMemory）

**当前实现进度**：D3 已完成 Chroma 集合初始化、显式向量写入、metadata 映射、按 ID 读取、持久化重开和基础用户隔离；D4 已完成三因子评分、时间衰减、命中记录、去重、软失效、物理删除和按用户删除。对应长期记忆测试 51/51 通过。

**职责**：跨会话记住关于用户的具体事实。

| 项 | 设计 |
|---|---|
| 存储 | Chroma 向量库 + SQLite 元数据 |
| 内容 | 抽取出的**结构化事实**，不是原始对话 |
| 检索 | 向量相似度 × 时间衰减 × 命中加权 |
| 写入 | 抽取 → 去重 → 冲突消解 |

**关键决策：为什么存"抽取的事实"而不是"原始对话"？**

| 维度 | 存原始对话 | 存抽取事实 |
|---|---|---|
| 检索精度 | 低（噪声大，聊天气泡混在一起） | 高（一条事实一个语义单元） |
| token 效率 | 差（找回一段话，有用的只有一句） | 好 |
| 可去重 | 几乎不可能 | 可以（同一事实合并） |
| 可冲突消解 | 不可能 | 可以（新旧事实标记生效期） |
| 可解释 | 差 | 好（能告诉用户"我记得你说过 X"） |
| 成本 | 低（不调 LLM） | 高（每次抽取都要调 LLM） |
| 错误风险 | 无 | 抽取可能出错，需校验兜底 |

结论：**精度和可控性上的收益远大于额外的抽取成本**，且错误可以用 pydantic 校验 + 置信度阈值兜底。

**事实的数据模型**：
```python
class ExtractedFact(BaseModel):
    subject: str          # 关于谁，通常是 "user"
    predicate: str        # 什么关系，如 "住在" / "喜欢" / "职业是"
    object: str           # 什么值，如 "杭州" / "喝咖啡" / "程序员"
    confidence: float     # 0~1，抽取置信度
    source_message_id: int  # 溯源：这条事实是从哪句话来的
    # 以下由系统填充
    created_at: datetime
    updated_at: datetime
    invalid_at: datetime | None   # 冲突消解后，旧事实证明失效的时间
    hit_count: int = 0            # 被检索命中的次数，用于识别"重要记忆"
    last_hit_at: datetime | None
```

**为什么要有 `subject`？**
为了将来支持多用户 / 多人对话（"我老婆喜欢辣"里的 subject 是"老婆"而不是"user"）。
现在只实现 `subject="user"`，但结构上留好扩展位。

**检索评分公式**：
```
final_score = similarity
            × decay(days_since_last_hit)      # 时间衰减
            × (1 + log(1 + hit_count) * 0.1)  # 常用记忆加权
```

时间衰减用指数衰减：
```python
def decay(days: float, half_life: float = 30.0) -> float:
    """半衰期 30 天：30 天没被用到的记忆，权重降到 0.5。"""
    return 0.5 ** (days / half_life)
```

**为什么要衰减？**
1. 用户半年没提过的偏好，很可能已经变了（"我养猫" → 猫可能已经不在了）
2. 防止向量库里陈旧记忆永远压着新记忆
3. 让"最近提到过的事"自然获得更高优先级

**为什么用 `hit_count` 加权？**
"我的名字是 X" 会被反复命中，"我上周三下午三点要开会"只命中一次。
前者是核心身份信息，应该在候选排序里更靠前。用对数加权避免高频记忆完全霸榜。

**已识别的改进方向：混合检索**（⭐ 本项目**未实现**，作为可选扩展保留）

- 纯向量：语义好，但对精确匹配（人名、编号、专有名词）差
- 加 BM25 关键词：补上精确匹配
- 融合：RRF（Reciprocal Rank Fusion）或简单加权

> **为什么没做**：实测中文 BGE 在 4/4 个中文语义查询上命中正确（见第 12 节），
> 而本项目的事实都是短句、词汇重叠高，混合检索的收益有限——它解决的是
> "专有名词检索"这个更窄的问题。
>
> 留着这一段是因为面试时它是个好话题：**能说清"为什么不做"比"做了什么"更值钱**，
> 而且要说得出它在什么条件下才值得做。

### 3.4 用户画像（UserProfile）

**职责**：稳定、便宜、可控地保存"这个人是谁"。

| 项 | 设计 |
|---|---|
| 存储 | SQLite 单行 JSON，或一张宽表 |
| 更新 | 增量合并（不是覆盖） |
| 注入 | 每轮都注入（因为量小且重要） |

**为什么已经有了长期记忆，还要单独做画像？**

1. **成本**：画像每轮无条件注入，不用做向量检索，省一次检索开销
2. **稳定**：核心身份信息（名字、职业）绝不能因为检索没命中就丢失
3. **可控**：结构化字段可以直接展示给用户看、让用户改（"我改主意了"）
4. **可校验**：pydantic 强类型，脏数据进不来

**画像模型**：
```python
class UserProfile(BaseModel):
    name: str | None = None
    city: str | None = None
    occupation: str | None = None
    preferences: list[str] = []      # 喜欢的
    dislikes: list[str] = []         # 讨厌的
    communication_style: str | None = None  # 如 "喜欢简短回答"
    updated_at: datetime | None = None
```

**增量合并规则**：
- 标量字段（name/city/...）：新值非空就更新，记录旧值到历史
- 列表字段（preferences/dislikes）：**并集**，而不是覆盖
- 冲突（如 "喜欢咖啡" 和 "戒咖啡了"）：走冲突消解流程，不是简单覆盖

## 4. 读写路径

### 4.1 读路径（每轮请求）

```
1. 取 system prompt                     （固定开销）
2. 取用户画像                            （结构化，量小）
3. 用「用户当前问题」做向量检索长期记忆    （top-k，按预算截断）
4. 取中期摘要                            （量中等）
5. 取短期窗口                            （最新 N 轮）
6. 按预算表裁剪，组装成最终 messages
7. 发给模型
```

**优化点**：步骤 2/3/4/5 之间没有依赖，可以**并行**取。
当前实现是**串行**的（简单、好调试）。暴露成 HTTP 接口时可以用
`asyncio.gather` 并发，把延迟从 `sum(t)` 降到 `max(t)`。

### 4.2 写路径（每轮结束后）

**核心决策：热路径 vs 后台？**

| 方案 | 优点 | 缺点 |
|---|---|---|
| **热路径**：用户说完立刻抽取 | 记忆即时可用；逻辑简单 | 每轮多一次 LLM 调用，用户多等 1–2 秒 |
| **后台**：异步批量抽取 | 用户无感；可攒批降成本 | 记忆有延迟；进程崩溃可能丢；实现复杂 |

**本项目的选择：全部走热路径。**

- 短期记忆：纯内存操作，几乎无成本
- 长期事实：每轮结束调一次模型抽取，实测增加约 1–2 秒

> **为什么选热路径**：这是个人助理场景，对话轮次不密集，1–2 秒可以接受；
> 而**热路径的逻辑简单得多**——后台模式要处理"进程崩溃时未落库的批次"、
> 要保证任务不重复执行，引入的复杂度远超它省下的那点延迟。
>
> **代价是真实的**，所以命令行里留了 `--no-extract` 开关：需要快速演示时
> 可以关掉抽取。**承认代价并给出缓解手段，比假装没有代价好。**
>
> **面试话术**：
> *"我评估过后台批量抽取——能省调用次数、用户无感，但要处理进程崩溃时的
> 数据丢失和任务去重，复杂度不划算。我选了热路径，代价是每轮多 1–2 秒，
> 并留了一个开关可以关掉。这是一个明确的、我说得出理由的取舍。"*

## 5. Token 预算分配

整个 prompt 的预算 = `context_window × prompt_budget_ratio`（默认 64000 × 0.5 = 32000）。

| 组成部分 | 占比 | 预算 | 超预算时的处理 | 优先级 |
|---|---|---|---|---|
| 系统提示词 | 10% | 3200 | 固定，不可压缩 | 1（最高） |
| 用户画像 | 10% | 3200 | 字段按重要性排序，从低到高砍 | 2 |
| 长期记忆 | 20% | 6400 | 按综合分数排序取 top-k | 5（最低） |
| 中期摘要 | 20% | 6400 | 当前实现按 token 上限截断并加省略号 | 4 |
| 近期对话 | 40% | 12800 | 从最老的开始丢弃 | 3 |

**为什么这么分？**

- **系统提示词不可压缩**，它的作用是定义 Agent 的行为边界，压缩它等于改变 Agent 性格
- **画像和摘要优先级高于长期记忆**：前者是"稳定身份"，后者是"可能相关的细节"。
  宁可少注入两条记忆，也不能忘记用户叫什么
- **近期对话拿最大份额**：因为最近几轮几乎总是最相关的，这是性价比最高的 token 支出
- **长期记忆优先级最低**：它是"锦上添花"，而且本身有置信度，砍掉影响最小

**实现**：
```python
@dataclass
class TokenBudget:
    total: int
    ratios: dict[str, float]   # 各部分的占比

    def allocate(self, part: str) -> int:
        """返回某一部分的 token 配额。"""
        ...
```

每次请求打印一张"预算执行报告"：
```
[预算报告] 总预算 32000
  system     实际  1200 / 配额  3200   ✅
  profile     实际   380 / 配额  3200   ✅
  long_term   实际  5400 / 配额  6400   ✅  (命中 8 条，注入 6 条)
  summary     实际  2100 / 配额  6400   ✅
  recent      实际 11200 / 配额 12800   ✅  (12 轮，保留 11 轮)
  ------------------------------------------------
  合计       20280 / 32000  (63%)
```

这张表是面试时最有说服力的东西之一 —— 它把"我做了记忆"变成"我的记忆是**受控**的"。

## 6. 记忆治理

### 6.1 去重

**问题**：用户反复说"我住在杭州"，不去重就会存几十条一样的记忆，污染向量库并挤占预算。

**方案**：新事实写入前，先检索相似事实：
- `similarity > 0.95` → 视为重复：不新增，只更新 `updated_at` 和 `hit_count`
- `0.75 < similarity ≤ 0.95` → 送到冲突消解流程判断
- `similarity ≤ 0.75` → 新事实，直接写入

### 6.2 冲突消解 ⭐

**场景**：用户先说"我住在杭州"，几天后说"我搬到上海了"。

这是**记忆系统最核心的难题**，也是面试必问的问题。如果不处理，库里会同时存在
"住在杭州"和"搬到上海"两条有效事实，检索时两条都返回，模型自己都矛盾。

#### 实施版本：规则版（本项目采用）

**判断规则**：

```
如果 新事实.predicate == 已有事实.predicate
   且 新事实.object  != 已有事实.object
→ 判定为冲突 → 旧事实设 invalid_at=now，新事实生效
```

**为什么用规则版而不是 LLM 裁决**（成本 20%，覆盖 80%）：

| 方案 | 成本 | 覆盖 | 说明 |
|---|---|---|---|
| **规则版**（采用） | 2.5 小时 | 约 80% | 不需要 LLM、不需要 prompt 设计、不会失败、结果完全可预测 |
| LLM 裁决 | 1 天 | 约 95% | 要设计 prompt + pydantic 结构化输出 + 失败处理 + 三种关系判断 |

规则版的覆盖面：
- ✅ "住在 杭州" → "住在 上海"
- ✅ "职业是 后端" → "职业是 前端"
- ⚠️ "喜欢 咖啡" → "戒了 咖啡"（predicate 不同，规则漏掉；但相似度可能 ≥0.95 被走去重合并）
- ❌ "我养了猫" → "猫送人了"（完全不同的话题，两条都保留是对的）

**面试时的讲法**：

> "冲突消解我先做的是规则版：`predicate` 相同、`object` 不同就判定为用户改主意了，
> 旧事实标记失效而不是删除 —— 标记失效可以回溯'你什么时候改的'，也方便误判时恢复。
>
> 我评估过用 LLM 判断'重复 / 补充 / 冲突'三种关系，能覆盖到 95%，
> 但成本是规则版的 4 倍，而且要处理模型输出不可靠的问题。
> 在'个人助手'这个场景里，改主意绝大多数就发生在同一个 predicate 上，
> 所以**我先用 20% 的成本拿到 80% 的收益**，把 LLM 裁决留作后续优化。"
>
> —— 这句话展示的是**工程判断力**，比"我用了 LLM 所以更先进"有说服力得多。

#### 完整版（后续可选）

三种关系，让 LLM 判断（用 pydantic 约束的结构化输出）：

| 关系 | 判断依据 | 处理 |
|---|---|---|
| `duplicate` 重复 | 说的是同一件事 | 更新 `updated_at`，`hit_count += 1` |
| `complement` 补充 | 新信息扩展了旧信息 | 两条都保留 |
| `contradict` 冲突 | 新信息否定了旧信息 | 旧事实设 `invalid_at=now`，新事实生效 |

**为什么用"标记失效"而不是"物理删除"？**（这一点两个版本都适用）
1. **可回溯**：能回答"你之前说过 X，什么时候改的？"
2. **防误判**：判断错了可以把 `invalid_at` 清空恢复
3. **可审计**：调试记忆问题时能看到完整历史

**LLM 版的 Prompt 要点**：必须给模型"这三种关系"的明确定义和一个例子，
否则它会倾向于把所有相似的事都判成 duplicate。

### 6.3 遗忘

机制从温和到激进。**本项目实现了前两个**：

| 机制 | 触发条件 | 动作 | 目的 | 本项目 |
|---|---|---|---|---|
| 时间衰减 | 持续生效 | 降低检索排序权重 | 让陈旧记忆自然沉底 | ✅ 已实现 |
| 显式遗忘 | 用户执行 `/forget` 或说"忘掉这个" | 标记删除 + 从向量库移除 | 尊重用户意愿（"被遗忘权"）| ✅ 已实现 |
| TTL | 事实带 `expires_at` 且已过期 | 标记失效 | 处理有时效的信息 | ⬜ 可选 |
| 低频淘汰 | `hit_count == 0` 且超过 90 天 | 移到归档表（不删） | 控制向量库规模 | ❌ 不做 |

> **为什么低频淘汰不做**：个人项目的量级撑死几千条事实，向量库膨胀不是问题。
> 它是为"百万级记忆"准备的机制，用在这里属于过度设计。
>
> **为什么 TTL 降级为可选**：抽取的 prompt 已经明确排除了"一次性的临时安排"
> （"我下周三要交报告"这类**根本不会被存成事实**），所以 TTL 只是模型偶尔
> 不听话时的安全网。它的价值比最初估计的**低**——这是设计评审时的修正。
>
> 注意：`facts` 表里已经留了 `expires_at` 列，目前没有任何代码填它。
> 要么补上实现，要么在文档里明确它是预留字段——**不要留一个"看起来能用
> 其实没人写"的字段，那比没有更容易误导人。**

**必须有的能力：显式遗忘。**
用户说"忘掉我刚才说的"，系统必须真的忘掉，并且**要能从向量库、SQLite、画像里全部删干净**。
这是一个很好的面试加分点——它体现产品意识和数据合规意识。

## 7. 存储 Schema

```sql
-- 会话
CREATE TABLE sessions (
    id          TEXT PRIMARY KEY,
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 消息（短期记忆的持久化）
CREATE TABLE messages (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id  TEXT NOT NULL REFERENCES sessions(id),
    role        TEXT NOT NULL CHECK (role IN ('system','user','assistant','tool')),
    content     TEXT NOT NULL,
    token_count INTEGER,
    created_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_messages_session ON messages(session_id, id);

-- 中期摘要
CREATE TABLE summaries (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id      TEXT NOT NULL REFERENCES sessions(id),
    content         TEXT NOT NULL,
    covered_until   INTEGER NOT NULL,   -- 摘要覆盖到哪条 message id
    created_at      TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 长期事实（向量存在 Chroma，结构化字段在这里）
CREATE TABLE facts (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    subject           TEXT NOT NULL DEFAULT 'user',
    predicate         TEXT NOT NULL,
    object            TEXT NOT NULL,
    confidence        REAL NOT NULL,
    source_message_id INTEGER,
    created_at        TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at        TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    invalid_at        TIMESTAMP,
    expires_at        TIMESTAMP,
    hit_count         INTEGER NOT NULL DEFAULT 0,
    last_hit_at       TIMESTAMP
);
CREATE INDEX idx_facts_valid ON facts(invalid_at, expires_at);

-- 用户画像（一个用户一行 JSON）
CREATE TABLE profiles (
    user_id     TEXT PRIMARY KEY,
    data        TEXT NOT NULL,          -- JSON
    updated_at  TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- 调用日志（成本与可观测）
CREATE TABLE llm_calls (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id          TEXT,
    purpose             TEXT,           -- 'chat' / 'summarize' / 'extract' / 'resolve'
    model               TEXT,
    prompt_tokens       INTEGER,
    completion_tokens   INTEGER,
    latency_ms          INTEGER,
    created_at          TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

**设计说明**：
- `purpose` 字段让成本能按用途拆分。你会看到"抽取事实"花掉的钱可能比"聊天"还多——
  这个数据会直接影响你的架构决策（比如改成批量抽取）
- `covered_until` 让摘要知道"我已经压缩到哪了"，避免重复压缩

## 10. 已知风险与取舍

| 风险 | 影响 | 缓解 |
|---|---|---|
| token 估算有误差 | 可能超出真实窗口被 API 拒绝 | 预算只用窗口的 50%，留足余量 |
| 递归摘要累积误差 | 早期信息逐渐失真 | 当前 prompt 保留关键信息；后续可加入结构化摘要，并用评测集验证长期召回 |
| 事实抽取出错 | 记忆里有错误信息 | pydantic 校验 + 置信度阈值 + 用户可查看可删改 |
| 冲突消解误判 | 把补充判成冲突，丢信息 | 标记失效而非删除，可恢复 |
| 向量检索漏召 | 需要的信息没被检索到 | 提高 `top_k` + 时间衰减让重要事实靠前；混合检索是已识别的后续方向（见 3.3）|
| LLM 抽取成本高于聊天 | 成本失控 | `llm_calls` 表按用途统计，必要时改批量抽取 |
| 记忆注入反而干扰 | 模型被无关记忆带偏 | 评测集含"无需记忆"用例，验证不退化 |

## 12. 向量模型选型（实测记录）

> 这一节记录的是**跑出来的数据**，不是查文档抄的结论。
> 面试时这类"我自己测过，结论和文档说的不一样"的内容，比复述概念有说服力得多。

### 12.1 问题：DeepSeek 没有 embedding 接口

DeepSeek 只提供对话模型，**没有任何向量化模型**
（参考 [DeepSeek-V3 issue #806](https://github.com/deepseek-ai/DeepSeek-V3/issues/806)）。
所以"我有 DeepSeek 的 key"只解决了聊天，解决不了检索 —— 向量必须另找来源。

候选方案：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Chroma 默认的 `all-MiniLM-L6-v2` | 零配置，自动下载 | **英文模型，中文效果差** | ❌ 实测淘汰 |
| `sentence-transformers` + 中文模型 | 生态成熟 | 要装 PyTorch，2GB+ | ❌ 对个人项目太重 |
| `fastembed` + `BAAI/bge-small-zh-v1.5` | 纯 ONNX，90MB，中文优化 | 首次要下载 | ✅ **采用** |
| 别家的 embedding API | 免下载、效果好 | 要多一个 key、多一份钱 | ⏸ 留作备选 |

### 12.2 实测：英文模型 vs 中文模型

**方法**：4 条候选句，用自然语言改写的方式提问（和候选句几乎没有字面重合），
看正确的那条能不能排到第一。

```
候选句：
  A. 我喜欢喝手冲咖啡，不加糖
  B. 我养了一只橘猫叫豆豆
  C. 我对花生过敏，点菜要注意
  D. 相对论描述了时空的几何结构
```

| 查询 | 英文 MiniLM 结果 | 中文 BGE-small-zh 结果 |
|---|---|---|
| 我平时喝什么**咖啡**？ | 咖啡句排 **第 3**（0.64）<br>输给 B(0.68) 和 C(0.68) ❌ | 咖啡句排 **第 1**（0.67）<br>第 2 名只有 0.33 ✅ |
| 我家**猫咪**叫什么名字？ | 猫句排 **第 2**（0.56）<br>输给 C(0.61) ❌ | 猫句排 **第 1**（0.66）<br>第 2 名 0.28 ✅ |
| 我吃**花生**会怎么样？ | 过敏句排 **第 1**（0.89）✅ | 过敏句排 **第 1**（0.64）✅ |
| 无关查询最高分 | 0.59（**几乎无区分度**） | 0.39（明显低于相关的 0.64） |

**结论**：

1. 英文模型只在**字面有重合**时有效（"花生"两个字都在）。
   一旦要做语义改写（"喝什么咖啡" → "喜欢喝手冲咖啡"，零字面重合）就完全失效。
2. 英文模型的无关查询最高分 0.59，而相关查询才 0.64 —— **几乎没有区分度**，
   这意味着检索结果接近于随机抽签。
3. 中文 BGE 模型：**4/4 命中，且相关与无关有明显分数带分离**（0.64+ vs 0.39）。

> ⚠️ 另一个反直觉的实测结果：BGE 官方建议给 query 加指令前缀
> （"为这个句子生成表示以用于检索相关文章："），但在 bge-**small**-zh-v1.5 上
> 实测**反而略微变差**：咖啡查询 不加前缀 0.6694 > 加前缀 0.6283。
> 所以我们默认不加前缀。
> **教训：不要迷信文档里的建议，要用自己的数据验证。**

### 12.3 工程实现中的三个坑

**坑 1：HuggingFace 在国内连不上**

| 站点 | 实测结果 |
|---|---|
| huggingface.co | 12 秒超时，不可达 |
| hf-mirror.com | 330 毫秒，可达 ✅ |
| modelscope.cn | 273 毫秒，可达 ✅ |

**坑 2：环境变量在模块 import 时会被"冻结"**

`huggingface_hub` 在模块顶层这样读配置：

```python
# constants.py:69
ENDPOINT = os.getenv("HF_ENDPOINT", "https://huggingface.co").rstrip("/")
# constants.py:282
HF_HUB_DISABLE_SYMLINKS_WARNING: bool = _is_true(os.environ.get(...))
```

也就是说：**只要它被 import 过一次，之后再改 `os.environ` 就完全无效了。**
症状是"我明明设了环境变量却不生效"，极难排查。

> 这是一条通用规律：**任何在模块顶层用 `os.getenv()` 读的配置，都会在 import 那一刻被冻结。**

我们的处理是两手都做，让调用方完全不用操心导入顺序：

1. 先在 `os.environ` 里设好 —— 应对"还没被 import"的正常情况
2. 再检查是否已经被 import，是就直接改它的模块常量 —— 应对"已经被 import"的最坏情况

实测验证：故意先 `import huggingface_hub`（制造最坏顺序），
再用全新缓存目录下载 —— 依然成功走镜像（22 秒下完 5 个文件），
且符号链接警告被成功抑制（捕获到的警告数 = 0）。

**坑 3：模型缓存默认放在系统临时目录**

`fastembed` 的默认缓存位置是 `%TEMP%`，而临时目录会被清理。
模型有 90MB，重下一次很烦。我们强制把它指向项目内的 `data/models/`。

### 12.4 这一节在面试里怎么讲

> "向量模型这块我踩了几个坑。
>
> 首先 DeepSeek 没有 embedding 接口，所以聊天和检索必须用两套模型。
> 其次 Chroma 自带的默认向量模型是英文的，我实测发现它在中文上基本不可用 ——
> 问'我平时喝什么咖啡'，它会把'我养了一只橘猫'排在第一位，因为它只在字面重合时有效。
> 我换成中文 BGE 小模型之后，语义改写的场景 4 条全中，而且相关和无关的分数带明显分开了。
>
> 还有一个坑是 HuggingFace 在国内连不上，必须用镜像。
> 更麻烦的是 huggingface_hub 在 import 时就把端点读成了模块常量，
> 所以如果它在你的代码之前被导入，环境变量就失效了。
> 我的做法是在设置环境变量的同时，检测它是否已被导入，是就把常量也改掉 ——
> 这样调用方不需要关心导入顺序。"
